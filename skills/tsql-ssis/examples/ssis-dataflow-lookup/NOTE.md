# ssis-dataflow-lookup: `LoadPaymentFact.dtsx`

Source: `source.dtsx` — a hand-written, `.dtsx`-shaped package description (the Sybase fixture has no SSIS packages; element names follow the DTS namespace so the §1/§2 XPath rules apply to it unchanged). Converted: `converted.sql` (Lakeflow Spark Declarative Pipelines SQL) plus `converted.yml` (the pipeline resource, the daily job that runs it as a `pipeline_task`, and the `OnError` handler's `etl_log` write as a failure task).

## Constructs exercised
- Data Flow Task with **OLE DB Source** (`AccessMode=2` SQL command, two `?` parameters bound to `User::LoadDate`) -> `CREATE TEMPORARY VIEW ... FROM STREAM(payments)`: the `LoadDate` window was the package's incremental bookmark (one day per run, no `TRUNCATE`), and the streaming checkpoint replaces it (SKILL §2b "SSIS Data Flow" lineage row, §6 decision table append/incremental -> ST; `databricks-pipelines` temporary-view-sql.md, streaming-table-sql.md). `load_date` is derived as `CAST(payment_date AS DATE)`, which equals `User::LoadDate` for every row the source window admitted.
- **Lookup** (`CacheType=0` Full cache, `NoMatchBehavior=1` redirect, parameterised reference query on `Package::ServicerId`) -> stream-static `LEFT JOIN` (`loans` read as a static snapshot at stream start, one snapshot per triggered update == one Full-cache load per package execution) + `lkp_loan_id IS NULL` routing (SKILL §6 "SSIS Lookup", §7 "Lookup cache mode vs collation"; streaming-table-sql.md "Stream-static join").
- **Derived Column** expressions `YEAR()*100+MONTH()`, `? :` ternary, nested ternary, `(DT_WSTR,4)TRIM()` -> `year()/month()`, boolean expression, `CASE`, `trim()` (SKILL §6 "SSIS Derived Column").
- **OLE DB Destination** fast load, append (`FastLoadOptions`, `FastLoadKeepNulls=false`, no truncate step) -> persistent `CREATE OR REFRESH STREAMING TABLE ... CLUSTER BY` with `coalesce` for the DW column default (`databricks-pipelines` streaming-table-sql.md; SKILL.md "Streaming Table: incremental processing, exactly-once, append-only"). A `MATERIALIZED VIEW` over the `${load_date}` window is the wrong form for this package: each refresh recomputes the defining query for the new day and the previous day's rows disappear from the destination, while the SSIS destination kept every day ever loaded. History is retained; a rerun of the same day appends nothing (checkpoint); re-loading history on purpose is a `full_refresh` of the table.
- **Lookup No Match Output -> second destination** -> `CONSTRAINT ... ON VIOLATION DROP ROW` on the fact plus a second persistent streaming table with the inverse predicate over the same streaming view; each streaming table has its own checkpoint, so every processed row lands in exactly one of the two (`databricks-pipelines` expectations-sql.md; SKILL §6 "SSIS error output").
- **OnError event handler** (Execute SQL Task into `dw.etl_log`) -> `sql_task` `log_onerror` in `converted.yml`, `run_if: AT_LEAST_ONE_FAILED` after the `pipeline_task`, writing the same `etl_log` row (`package_name`, `event = 'OnError'`, `message`, `logged_at`); the message carries `{{tasks.load_payment_fact.result_state}}` / `{{tasks.load_payment_fact.error_code}}` and the run id in place of `System::ErrorDescription` (docs `/jobs/dynamic-value-references`). The job `on_failure` notification is kept as an additional signal only (`databricks-jobs` notifications-monitoring.md; SKILL §6 "SSIS Event Handlers"). The table write is part of the customer's data contract (ops reads `etl_log`) and is never replaced by a notification.
- Two **connection managers** (`LOANSQL01/loan_servicing`, `LOANDW01/loan_mart`) -> two catalog/schema names in the mapping (SKILL §6 "SSIS Connection Managers"); `ProtectionLevel=DontSaveSensitive` recorded in §9 governance discovery.
- Package parameter (`ServicerId`, `Required="True"`, design value 7) -> job parameter `servicer_id` (default `"7"`) forwarded per run by `pipeline_task.parameters.servicer_id: "{{job.parameters.servicer_id}}"` and read in the pipeline SQL as `:servicer_id` (docs `/aws/en/jobs/pipeline` "Parameters", Beta; Jobs API `pipeline_task.parameters`; `/aws/en/jobs/parameter-use` named parameters in a pipeline task; SKILL §6 "SSIS Variables"). `Required="True"` means the executor passed the value on every execution (`dtexec /Par "$Package::ServicerId";7`, the SQL Agent job step), so the contract is *per run*; the Jobs equivalent is overriding the job parameter for a run ("Run now with different parameters" / API `job_parameters`), and the scheduled default reproduces what the Agent step passed. A pipeline `configuration` key (the previous shape) is deploy-time only: it froze `7` for every run and silently ignored any runtime selection. Fallback where the pipeline-task Parameters Beta is not enabled: one pipeline resource per servicer with `configuration.servicer_id` and `${servicer_id}` in the SQL, one `pipeline_task` each (comment in `converted.yml`). Variable `LoadDate` -> no key (bookmark replaced by the checkpoint, above); `RowsRead` (a row-count variable) has no consumer in the package and is dropped.

Writes: `loan_mart.dw.fact_payment`, `loan_mart.dw.err_payment_no_loan`, `loan_mart.dw.etl_log` (event handler). ## Recorded deltas (per-unit decisions, not reproduced)
- **Same-day rerun**: the source package had no idempotency key, so re-running it for a `LoadDate` appended that day twice; the checkpoint makes the converted rerun a no-op. Recon expects the source count only where the source ran once per day.
- **Late-arriving rows**: a payment inserted after its `payment_date` day had passed was never picked up by any source window; the stream loads it on the next update with `load_date = CAST(payment_date AS DATE)`. Reconcile `fact_payment` against `payments` (the truth) rather than against the legacy `dw.fact_payment` for those rows; the legacy fact is short by construction.
- **Initial load**: the first pipeline update reads all of `payments`, i.e. every daily window at once; if the legacy fact started later than the oldest payment, filter the first load with `WHERE payment_date >= <fact start>` or reconcile from that date.
- **OnError cardinality**: SSIS fired the handler once per error event (often several rows per failed run); the conversion writes exactly one `etl_log` row per failed run.
- **One servicer per day**: the per-run parameter matches the fixture's schedule (one execution per day, one `ServicerId`). A streaming table processes each `payments` row once, so if the real estate executed the package several times a day with different `ServicerId` values, the second execution's rows would already be checkpointed under the first servicer; that estate needs the per-servicer pipeline shape (separate checkpoints and destinations, or a `servicer_id` column in the fact) — the census must record the Agent step's `/Par` values before the shape is chosen.

## Recon tier that catches a wrong conversion
- **Tier 1**: `count(fact_payment) + count(err_payment_no_loan)` per `load_date` must equal the source row count of the OLE DB Source query for that day; the split between them is the Lookup's match/no-match count. An `INNER JOIN` instead of `LEFT JOIN` silently drops the no-match rows (`err_*` empty, fact short). **History check**: after N daily updates the destination holds N distinct `load_date` values with their day-1..N counts intact; the materialized-view conversion fails this on day 2 (only the latest `load_date` remains). **Rerun check**: trigger the pipeline twice for the same day; the per-`load_date` counts must not change.
- **Failure-injection run** (`etl_log` contract): make the pipeline task fail (e.g. a bad `servicer_id` type); `etl_log` must gain exactly one `('LoadPaymentFact', 'OnError', ...)` row for the run, and none on a clean run.
- **Parameter run** (`ServicerId` contract, Tier 1): run the job with `servicer_id` overridden to a servicer that owns no loans; the run must route every new payment to `err_payment_no_loan` and add nothing to `fact_payment`. A conversion that reads the servicer from pipeline `configuration` passes every other check and fails this one (it keeps loading servicer 7).
- **Tier 2**: null-rate on `investor_code`/`property_state` (0 by construction after DROP ROW), `sum(total_amt)` (catches a `coalesce` default applied to the wrong column), distinct-count of `amt_bucket` (3) and of `payment_month` (1 per load date).
- **Tier 3** keyed on `payment_id`: `amt_bucket` boundaries (`< 500` vs `<= 500`), `is_reversal`, `loan_type` trimmed vs padded (`rstrip_spaces` masks the padding difference only if applied — the tolerance record must say which side trims).
- Lookup cache-mode trap: if the real package were Partial/No cache on a CI database, the join would need `collation_casefold`; Full cache does not (§7).
