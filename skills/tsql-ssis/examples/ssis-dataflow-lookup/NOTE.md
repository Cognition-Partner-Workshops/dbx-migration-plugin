# ssis-dataflow-lookup: `LoadPaymentFact.dtsx`

Source: `source.dtsx` — a hand-written, `.dtsx`-shaped package description (the Sybase fixture has no SSIS packages; element names follow the DTS namespace so the §1/§2 XPath rules apply to it unchanged). Converted: `converted.sql` (a Lakeflow Jobs `sql_task` file: the run's `LoadDate` window read once with its lookup verdict into a session temp table, then two idempotent `MERGE` statements over it) plus `converted.yml` (the daily job with `src_catalog`/`src_schema` (loan_servicing), `tgt_catalog`/`tgt_schema` (loan_mart.dw), `load_date`, `servicer_id` job parameters and the `OnError` handler's `etl_log` write as a failure task).

## Execution model: parameterised bounded batch, not a streaming table
One package execution = one (`User::LoadDate` window, `$Package::ServicerId`) pair: the source re-read the whole day from `dbo.payments` on every execution and evaluated every row of it against **that servicer's** loans. Both values are per execution (`ServicerId` is `Required="True"`, i.e. passed by `dtexec /Par` from the Agent step; `LoadDate` is bound to the two `?` markers), so the target form is a job run with two job parameters and set-based DML that re-evaluates the window under those values (SKILL §6 "SSIS Data Flow" row: *per-execution parameter -> bounded batch*).

The previous shape (Lakeflow Spark Declarative Pipelines streaming tables over `STREAM(payments)` with `:servicer_id` forwarded through `pipeline_task.parameters`) was wrong for this package: a streaming table checkpoints the `payments` rows it has consumed once, globally, so a per-run filter cannot be re-applied to rows an earlier run already consumed. Run 1 with servicer 7 consumed the day and wrote servicer 12's payments to `err_payment_no_loan`; run 2 with servicer 12 then found nothing left to read, so its facts were lost and the wrong error rows stayed. A pipeline `configuration` key (the shape before that) froze the value at deploy time instead. Both defects come from the same mismatch: the parameter selects the row set on every run, and only a bounded batch re-selects.

## Constructs exercised
- Data Flow Task with **OLE DB Source** (`AccessMode=2` SQL command, two `?` parameters bound to `User::LoadDate`) -> the `CREATE TEMP TABLE lkp_window AS SELECT ... FROM IDENTIFIER(:src_catalog||'.'||:src_schema||'.payments')` statement, `WHERE payment_date >= CAST(:load_date AS TIMESTAMP_NTZ) AND payment_date < CAST(date_add(CAST(:load_date AS DATE), 1) AS TIMESTAMP_NTZ)` (docs `functions/date_add`), `load_date = CAST(:load_date AS DATE)` (SKILL §2b "SSIS Data Flow" lineage row; §6 "SSIS Data Flow"). `:load_date` is the job parameter (docs `/aws/en/jobs/parameter-use` "SQL: use named parameters to retrieve parameter values"; `/aws/en/jobs/sql` task parameters).
- **Lookup** (`CacheType=0` Full cache, `NoMatchBehavior=1` redirect, parameterised reference query on `Package::ServicerId`) -> `LEFT JOIN loans ON loan_id AND servicer_id = CAST(:servicer_id AS INT)` in the one `CREATE TEMP TABLE lkp_window AS SELECT` statement, with `matched = l.loan_id IS NOT NULL` as the Match / No Match verdict; the two `MERGE`s then read `WHERE matched` / `WHERE NOT matched` from `lkp_window`. One statement reads one Delta snapshot of `payments` and one of `loans` (docs `/optimizations/isolation/isolation-levels`), which is the Full-cache contract: one point-in-time load of the reference set per execution, every row of the window in exactly one output. Two `MERGE`s each reading `loans` themselves (an earlier shape) read two snapshots, so a loan inserted, deleted or re-serviced between them landed a payment in both outputs or in neither. The temp table is session-scoped, created by CTAS without catalog privileges and dropped at the end of the file (`databricks-dbsql` materialized-views-pipes.md "Temporary Tables"; `CREATE OR REPLACE TEMP TABLE` is unsupported, hence `DROP TABLE IF EXISTS` first). Where the tables and warehouse support it, both `MERGE`s inside one `BEGIN ATOMIC ... END` block is the documented alternative (repeatable reads inside the block, docs `/transactions`) (SKILL §6 "SSIS Lookup", §7 "Lookup cache mode vs collation"; Full cache compares in .NET, case- and space-sensitive, so no collation folding).
- **Derived Column** expressions `YEAR()*100+MONTH()`, `? :` ternary, nested ternary, `(DT_WSTR,4)TRIM()` -> `year()/month()`, boolean expression, `CASE`, `trim()` (SKILL §6 "SSIS Derived Column").
- **OLE DB Destination** fast load, append (`FastLoadOptions`, `FastLoadKeepNulls=false`, no truncate step) -> `MERGE INTO IDENTIFIER(:tgt_catalog||'.'||:tgt_schema||'.fact_payment') ... WHEN NOT MATCHED THEN INSERT` keyed on `payment_id` (docs `delta-merge-into`; `sql-ref-names-identifier-clause`: `IDENTIFIER` as the MERGE target and in the query) with `coalesce` for the DW column default. The destination keeps every day ever loaded (append package), a rerun of the same `(load_date, servicer_id)` inserts nothing, and re-loading one historical day is the same run with `load_date` overridden.
- **Lookup No Match Output -> second destination** -> the second `MERGE` into `err_payment_no_loan`, keyed on `(payment_id, servicer_id)`: "payment X has no loan under servicer S" is one fact per servicer, which is exactly one row per source execution. `servicer_id` is an **added column** on the error table (the source table had no key at all; recorded delta below). The two statements partition the window the way the Lookup's two outputs did (SKILL §6 "SSIS error output").
- **OnError event handler** (Execute SQL Task into `dw.etl_log`) -> `sql_task` `log_onerror` in `converted.yml`, `run_if: AT_LEAST_ONE_FAILED` after the load task, writing the same `etl_log` row (`package_name`, `event = 'OnError'`, `message`, `logged_at`); the message carries `{{tasks.load_payment_fact.result_state}}` / `{{tasks.load_payment_fact.error_code}}` and the run id in place of `System::ErrorDescription` (docs `/jobs/dynamic-value-references`). The job `on_failure` notification is kept as an additional signal only (`databricks-jobs` notifications-monitoring.md; SKILL §6 "SSIS Event Handlers"). The table write is part of the customer's data contract (ops reads `etl_log`) and is never replaced by a notification.
- Two **connection managers** (`OLTP_LoanServicing` = `LOANSQL01/loan_servicing`, `DW_LoanMart` = `LOANDW01/loan_mart`) -> two namespaces carried as two job-parameter pairs: `src_catalog`/`src_schema` for every `payments`/`loans` read (the migrated `loan_servicing.dbo`, read only), `tgt_catalog`/`tgt_schema` for the `MERGE` targets and the `etl_log` write (`loan_mart.dw`) (SKILL §6 "SSIS Connection Managers"). One catalog/schema pair for both would make the fact load read its own namespace for `payments`/`loans` and fail or read unrelated tables. `ProtectionLevel=DontSaveSensitive` recorded in §9 governance discovery.
- Package parameter (`ServicerId`, `Required="True"`, design value 7) -> job parameter `servicer_id` (default `"7"`, what the Agent step passed) consumed as `:servicer_id` through `sql_task.parameters` (SKILL §6 "SSIS Variables"). `Required="True"` means the executor passed the value on every execution, so the contract is *per run*; the Jobs equivalent is overriding the job parameter for a run ("Run now with different parameters" / API `job_parameters`), and two servicers a day are two runs (or two `run_job_task` calls), each re-reading the same window under its own value. Variable `LoadDate` -> job parameter `load_date`, default `{{job.start_time.iso_date}}` (INFERRED stand-in for the Agent step's `/Set`; the census reads the step); `RowsRead` (a row-count variable) has no consumer in the package and is dropped.
- **Concurrency**: `max_concurrent_runs: 1` (an SSIS package is not re-entrant) serialises runs of *this job* only; it does not fence writers to `loan_servicing` (the single-snapshot `lkp_window` handles those: a concurrent `loans` write is either in the snapshot or not, as it was either in the SSIS cache or not) nor writers to the `dw` tables. An outside writer to either destination makes a `MERGE` fail at commit (docs `/optimizations/isolation/row-level-concurrency`: `MERGE` + `MERGE` can conflict) and `max_retries: 2` re-runs the task, which rebuilds `lkp_window` and re-runs both idempotent `MERGE`s. A failure between the two `MERGE`s leaves the fact loaded and the error rows missing, the same non-transactional state a mid-flow SSIS failure left (`TransactionOption=Supported`, no enclosing transaction in the package); the rerun repairs it.
- SSIS type codes `cy` (currency = `MONEY`), `str`/`wstr` with `codePage`, `dbTimeStamp`, `dbDate`, `i4`, `bool` -> §4 type map rows.

## Lineage (FACT)
Reads: `loan_servicing.dbo.payments` (SqlCommand), `loan_servicing.dbo.loans` (Lookup reference). Writes: `loan_mart.dw.fact_payment`, `loan_mart.dw.err_payment_no_loan`, `loan_mart.dw.etl_log` (event handler). The executable carries the same split: reads through `:src_catalog.:src_schema`, writes through `:tgt_catalog.:tgt_schema`. Unit = the package + both destinations; `fact_payment` is shared if another package or procedure writes it (none in this fixture).

## Recorded deltas (per-unit decisions, not reproduced)
- **Same-day rerun**: the source package had no idempotency key, so re-running it for a `LoadDate` appended that day twice; the `MERGE` keys make the converted rerun a no-op. Recon expects the source count only where the source ran once per (day, servicer).
- **Error-table key**: `err_payment_no_loan` gains a `servicer_id` column (the run's `$Package::ServicerId`) so its rows have an identity and a run for a second servicer over the same window adds its own rows without duplicating the first's. Legacy readers that `SELECT *` see one more column.
- **Servicer transfer**: if a loan moved between servicers and the package ran once per servicer over the same window, the source could insert the same payment into the fact twice (once per matching run); the `payment_id` key keeps the first. The census must confirm whether `loans.servicer_id` changes (the fixture's `sp_loan_modification` does not touch it).
- **Late-arriving rows**: a payment inserted after its `payment_date` day had passed was never picked up by any source window, and the bounded batch reproduces that gap deliberately (same window, same miss). Reconcile `fact_payment` against the legacy `dw.fact_payment` row for row; a late payment needs an explicit re-run of its day, as it did on the source.
- **Initial load**: history is loaded by running the job once per historical day (a `for_each_task` over the date list, `databricks-jobs` task-types.md) or by a one-off backfill, never by a streaming full refresh.
- **OnError cardinality**: SSIS fired the handler once per error event (often several rows per failed run); the conversion writes exactly one `etl_log` row per failed run.

## Recon tier that catches a wrong conversion
- **Tier 1**: `count(fact_payment) + count(err_payment_no_loan WHERE servicer_id = S)` per `load_date` must equal the source row count of the OLE DB Source query for that day; the split between them is the Lookup's match/no-match count for servicer S. A conversion without the No Match branch silently drops the no-match rows; a conversion whose two outputs read `loans` on two snapshots fails the equality under a concurrent `loans` write (a payment counted twice or not at all), so run this check once with a loan inserted for the servicer while the job is running: `fact + err` must still equal the source count. **History check**: after N daily runs the destination holds N distinct `load_date` values with their day-1..N counts intact. **Rerun check**: run the job twice for the same `(load_date, servicer_id)`; no count changes.
- **Two-servicer run** (the execution-model check, Tier 1): run the job for the same `load_date` with `servicer_id = 7` and then `servicer_id = 12`. Afterwards `fact_payment` must hold servicer 12's matches for that day and `err_payment_no_loan` must hold one row per (unmatched payment, servicer). A streaming-table conversion fails this: the second run finds nothing to read, so servicer 12's facts are missing and its payments sit in the error table under the first run.
- **Parameter run** (`ServicerId` contract, Tier 1): run the job with `servicer_id` overridden to a servicer that owns no loans; every payment of the window lands in `err_payment_no_loan` under that servicer and nothing is added to `fact_payment`. A conversion that reads the servicer from a deploy-time value passes every other check and fails this one.
- **Failure-injection run** (`etl_log` contract): make the load task fail (e.g. a non-numeric `servicer_id`); `etl_log` must gain exactly one `('LoadPaymentFact', 'OnError', ...)` row for the run, and none on a clean run.
- **Tier 2**: null-rate on `investor_code`/`property_state` (0 by construction: the fact only holds matched rows), `sum(total_amt)` (catches a `coalesce` default applied to the wrong column), distinct-count of `amt_bucket` (3) and of `payment_month` (1 per load date).
- **Tier 3** keyed on `payment_id`: `amt_bucket` boundaries (`< 500` vs `<= 500`), `is_reversal`, `loan_type` trimmed vs padded (`rstrip_spaces` masks the padding difference only if applied — the tolerance record must say which side trims).
- Lookup cache-mode trap: if the real package were Partial/No cache on a CI database, the join would need `collation_casefold`; Full cache does not (§7).

## INFERRED edges
The OnError handler's two `?` bindings are not shown in the package; `package_name` = `System::PackageName` and `message` = `System::ErrorDescription` are inferred (standard for this handler shape), the `etl_log` write itself is FACT. Connection strings are literal here; in a real project they are usually project parameters (INFERRED until the `.params` file is read). The `load_date` default is INFERRED from the daily schedule.
