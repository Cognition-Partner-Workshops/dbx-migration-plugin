## Constructs exercised

Every parameter carries a `p_` prefix: an unqualified name resolves as a column before a parameter/variable on Databricks (`[dbsql:names]`), so `l.servicer_id = servicer_id` or `p.batch_id = batch_id` would compare a column with itself and select every row (SKILL §7 "parameter shadowing").
- `@@identity` after the audit insert -> `uuid()` run key + `SELECT audit_id INTO` read-back (SKILL §5 row 74, §7 "@@identity hijacked by triggers").
- `SELECT ... INTO #eligible_loans` -> `CREATE TEMP TABLE` (SKILL §5 row 70).
- `DECLARE CURSOR` / `FETCH` / `WHILE @@sqlstatus = 0` / `CLOSE` / `DEALLOCATE CURSOR` -> one set-based `INSERT ... SELECT` + `MERGE` (SKILL §6 "cursor" row; delta list item 4).
- `@@error` + `GOTO error_handler` + cleanup -> `DECLARE EXIT HANDLER FOR SQLEXCEPTION` (SKILL §6 "error handling"; delta item 6).
- `RAISERROR 50001 'msg %1!', @batch_id` -> `DECLARE ... CONDITION FOR SQLSTATE '45001'` + `SIGNAL ... SET MESSAGE_TEXT` (delta item 5).
- Per-loan `BEGIN TRANSACTION ... COMMIT / ROLLBACK` -> compensating `EXIT HANDLER` (SKILL §6 "transactions"). The compound statement is `NOT ATOMIC` (`[dbsql:scripting]` "Key rules"), so the handler undoes only this invocation's writes, each behind an ownership predicate: `PAYMENT_INS` audit rows and `payments` owned by `batch_id`, and, only when the `balances_applied` flag shows the (single, atomic) `MERGE` ran, `loans.current_balance` is reversed by adding back `waterfall.principal_due` per loan. It is a delta reversal, never an absolute restore from the `eligible_loans` snapshot: a snapshot restore would erase any balance change a concurrent writer (`sp_insert_payment`, a modification) committed between snapshot and failure. Invariant preserved: no loan ever ends with a payment row but no balance update (the source's per-loan transaction guarantees exactly that). The `BATCH_START` row is deliberately **not** deleted: the source inserts it outside every transaction and `error_handler` never removes it, so a failed source run always leaves one `BATCH_START` row (`record_count` 0, `new_value` NULL because Step 4 never ran); the handler only clears the `run_key` from `new_value` so the converted row is column-for-column the source's failed-batch row, and the batch id survives for the `SIGNAL` message. **Commit-unit decision**: the source commits loan by loan, so a failure at loan k leaves 1..k-1 applied, and a rerun re-pays them (eligibility is not batch-aware). The set-based conversion makes the batch the commit unit: on failure nothing is applied, a state the source itself produces when loan 1 fails and the only one a rerun can start from safely. This is recorded per unit (SKILL §7 "Multi-table transaction flattened", decision column), not assumed. The `BEGIN ATOMIC ... END` route (Preview; every table `catalogManaged`) is noted in the file as the replacement once the tables are created with that property.
- `MONEY` arithmetic (`@current_bal * (@interest_rate / 12.0 / 100.0)`) -> `round(..., 4)` at each source rounding point (SKILL §7 "MONEY arithmetic").
- `ISNULL(e.total_escrow, $0.00)` -> `coalesce(..., CAST(0 AS DECIMAL(19,4)))` (§5 rows 1, 84).
- `@@rowcount` -> `SELECT count(*) INTO` (§5 row 75).
- Audit trigger fan-out: `trg_audit_payment` (FOR INSERT on `payments`) is folded into the writer (SKILL §2b "Triggers", §6 "audit trigger").
- `SUSER_NAME()` -> `current_user()`; `CONVERT(VARCHAR(20), money)` -> `cast(... AS STRING)`.

## Recon tier that catches a wrong conversion
- **Tier 2 (aggregates)** on `payments WHERE batch_id = <batch>`: `sum(principal_amt)`, `sum(interest_amt)`, `sum(escrow_amt)`, `count(*)` vs the source batch. Missing `round(..., 4)` shows as cent-level drift in `sum(interest_amt)` once `decimal_round` places=4 has removed scale noise; a wrong final-payment clamp shows in `sum(principal_amt)`.
- **Tier 1** on `audit_trail` rows per batch: 1 (`BATCH_START`) + N (`PAYMENT_INS`) — a conversion that forgets the trigger fold produces exactly 1.
- **Tier 3** keyed on `loans.loan_id`: `current_balance` after the run (the `MERGE` must subtract exactly once per loan; a cursor-faithful loop that double-applied would show here). A shadowed `p_servicer_id` (all servicers processed) shows first as a Tier 1 count delta on `payments WHERE batch_id = <batch>`.
- **Failure-injection replay** (Tier 4, on the migration catalog only): force the `MERGE` to fail (e.g. a NOT NULL violation via a seeded bad row) and assert Tier 1 on `payments` delta = 0, `audit_trail` delta = exactly 1 (the `BATCH_START` row with `record_count` 0 and `new_value` NULL, which is what the source's `error_handler` leaves too; a handler that deleted it, or one that left the `run_key` in `new_value`, both fail this Tier 3 on `audit_trail`) and Tier 3 on `loans.current_balance` = pre-run values (exclude `loans.modified_date`: the reversal does not restore it). A second replay with a concurrent balance write between the snapshot and the injected failure must keep that write (delta reversal), which the earlier snapshot-restore design would have erased. Without the compensating handler the first replay leaves N payments and N+1 audit rows with unchanged balances. A third replay that fails the snapshot itself (e.g. revoke `SELECT` on `escrow_accounts` in the migration catalog) must still leave that one `BATCH_START` row and return its `audit_id` in the error message: the converted statement order is the source's (Step 1 batch record, Step 2 snapshot), so a conversion that creates the temp table first fails this replay with `audit_trail` delta = 0. Not verifiable on the fixture.
