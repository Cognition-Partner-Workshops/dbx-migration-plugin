Source: fixture `stored_procs/Servicing/sp_process_monthly_payments.sql` (Sybase ASE 16). Converted: `converted.sql` (DBSQL `CREATE PROCEDURE` + SQL scripting; the same body runs as a `sql_task` if procedures are not enabled on the warehouse).

## Constructs exercised
- `OUTPUT` parameter (`@batch_id`) and `RETURN 0/1` -> `OUT p_batch_id`, `OUT p_rc` (SKILL §6 "CREATE PROCEDURE", "RETURN"). Every parameter carries a `p_` prefix: an unqualified name resolves as a column before a parameter/variable on Databricks (`[dbsql:names]`), so `l.servicer_id = servicer_id` or `p.batch_id = batch_id` would compare a column with itself and select every row (SKILL §7 "parameter shadowing").
- `@@identity` after the audit insert -> `uuid()` run key + `SELECT audit_id INTO` read-back (SKILL §5 row 74, §7 "@@identity hijacked by triggers").
- `SELECT ... INTO #eligible_loans` -> `CREATE TEMP TABLE` (SKILL §5 row 70).
- `DECLARE CURSOR` / `FETCH` / `WHILE @@sqlstatus = 0` / `CLOSE` / `DEALLOCATE CURSOR` -> one set-based `INSERT ... SELECT` + `MERGE` (SKILL §6 "cursor" row; delta list item 4).
- `@@error` + `GOTO error_handler` + cleanup -> `DECLARE EXIT HANDLER FOR SQLEXCEPTION` (SKILL §6 "error handling"; delta item 6).
- `RAISERROR 50001 'msg %1!', @batch_id` -> `DECLARE ... CONDITION FOR SQLSTATE '45001'` + `SIGNAL ... SET MESSAGE_TEXT` (delta item 5).
- Per-loan `BEGIN TRANSACTION ... COMMIT / ROLLBACK` -> one nested **`BEGIN ATOMIC ... END`** block around every write of the batch (`payments` INSERT, `PAYMENT_INS` audit INSERT, the balance guard, the `loans` MERGE, the Step 4 batch-record UPDATE), plus an `EXIT HANDLER` that only re-shapes the `BATCH_START` row and re-raises (SKILL §6 "transactions"). The compound statement is `NOT ATOMIC` (`[dbsql:scripting]` "Key rules"); the atomic block is the non-interactive transaction of docs `/aws/en/transactions/` + `/transactions/transaction-modes`: all statements commit together or roll back together, a `SIGNAL` inside it triggers the rollback, and reads inside it are repeatable (one snapshot per table at first access). **Why no compensation**: Databricks uses optimistic concurrency, so a compensating `balance + principal_due` after a failure could run against a balance another writer committed after this run started, corrupting that writer's result; the earlier delta-reversal handler had exactly this bug. With the block, a failure leaves nothing to compensate, and a concurrent update of any loan row the MERGE touches is a write-write conflict that fails this run's commit instead (docs "Conflict detection and concurrency", "Conflict scenarios"); the handler then raises SQLSTATE `45001` and the caller re-runs, which re-snapshots `eligible_loans` from fresh data (docs "Best practices": "Build retry logic"). Invariant preserved: no loan ever ends with a payment row but no balance update (the source's per-loan transaction guarantees exactly that). **Requirements** (docs "Requirements"; `[dbsql:scripting]` "Multi-Statement Transactions", Preview): `payments`, `audit_trail`, `loans` are Unity Catalog managed tables with catalog commits (`TBLPROPERTIES ('delta.feature.catalogManaged' = 'supported')` at creation; not upgradable in place), run on a SQL warehouse, serverless, or DBR 18.0+. **Fallback when a table cannot meet them** (documented, not the executable shape): compare-and-set, never blind reversal: the MERGE's `WHEN MATCHED AND t.current_balance = w.current_balance` (snapshot pre-image) stamps `t.modified_date` with one run-owned timestamp; a matched-row count below `count(waterfall)` means a concurrent writer changed a balance and the run `SIGNAL`s; the handler reverses only rows whose `modified_date` still equals the run's stamp and writes a `BALANCE_CONFLICT` audit row for any it left alone, so a concurrent writer's balance is never overwritten and the operator sees which loans need reconciliation. The `BATCH_START` row is deliberately written **outside** the block and **not** deleted: the source inserts it outside every transaction and `error_handler` never removes it, so a failed source run always leaves one `BATCH_START` row (`record_count` 0, `new_value` NULL because Step 4 never ran); the handler only clears the `run_key` from `new_value` so the converted row is column-for-column the source's failed-batch row, and the batch id survives for the `SIGNAL` message. **Commit-unit decision**: the source commits loan by loan, so a failure at loan k leaves 1..k-1 applied, and a rerun re-pays them (eligibility is not batch-aware). The set-based conversion makes the batch the commit unit: on failure nothing is applied, a state the source itself produces when loan 1 fails and the only one a rerun can start from safely. This is recorded per unit (SKILL §7 "Multi-table transaction flattened", decision column), not assumed.
- `MONEY` arithmetic (`@current_bal * (@interest_rate / 12.0 / 100.0)`) -> `round(..., 4)` at each source rounding point (SKILL §7 "MONEY arithmetic").
- `ISNULL(e.total_escrow, $0.00)` -> `coalesce(..., CAST(0 AS DECIMAL(19,4)))` (§5 rows 1, 84).
- `@@rowcount` -> `SELECT count(*) INTO` (§5 row 75).
- Audit trigger fan-out: `trg_audit_payment` (FOR INSERT on `payments`) is folded into the writer (SKILL §2b "Triggers", §6 "audit trigger").
- Validation trigger fan-out: `trg_validate_loan_amount` (FOR UPDATE on `loans`, `IF UPDATE(current_balance)`) is folded in as the Shape A pre-check from `examples/trigger-validate/converted.sql` immediately before the `loans` MERGE, **inside the same atomic block**: `IF EXISTS (post-image < 0 AND loan_status NOT IN ('CO','PO'))` -> `BALANCE_VIOLATION` audit row + `SIGNAL` SQLSTATE `'45050'` (source RAISERROR 50050 + ROLLBACK). Guard and MERGE read the same `loans` snapshot (docs "Transaction isolation"), so the guard validates exactly the post-image the MERGE writes; a balance committed by another writer between the two statements is impossible inside the snapshot and, if it commits first, fails this block at commit time instead of bypassing the check. The `SIGNAL` rolls the block back, `BALANCE_VIOLATION` row included, which is the source's end state too (its trigger's audit row was inside the rolled-back per-loan transaction). Every converted writer of `loans.current_balance` needs the same block (SKILL §2b "Triggers": the trigger's writes belong to every writer).
- `SUSER_NAME()` -> `current_user()`; `CONVERT(VARCHAR(20), money)` -> `cast(... AS STRING)`.

## Recon tier that catches a wrong conversion
- **Tier 2 (aggregates)** on `payments WHERE batch_id = <batch>`: `sum(principal_amt)`, `sum(interest_amt)`, `sum(escrow_amt)`, `count(*)` vs the source batch. Missing `round(..., 4)` shows as cent-level drift in `sum(interest_amt)` once `decimal_round` places=4 has removed scale noise; a wrong final-payment clamp shows in `sum(principal_amt)`.
- **Tier 1** on `audit_trail` rows per batch: 1 (`BATCH_START`) + N (`PAYMENT_INS`) — a conversion that forgets the trigger fold produces exactly 1.
- **Tier 2 invariant** from the fixture README: `count(*) FROM loans WHERE current_balance < 0 AND loan_status NOT IN ('CO','PO')` = 0 on both sides after the run. A conversion that drops the `trg_validate_loan_amount` pre-check passes Tier 1-3 on normal data and fails only this invariant (and the replay below) once a concurrent balance change makes a waterfall row overdraw. Replay (Tier 4, migration catalog only): lower one eligible loan's `current_balance` below its `principal_due` between the `eligible_loans` snapshot and the atomic block (or seed it that way and bypass the waterfall clamp); expect `payments` delta 0, `BALANCE_VIOLATION` delta 0 (rolled back with the block, as on the source), `BATCH_START` kept, `p_rc = 1`, `loans` unchanged. A conversion that runs the guard and the MERGE as two statements outside a transaction passes this replay but fails the **concurrent-writer replay**: commit an UPDATE to one waterfall loan's `current_balance` after the guard evaluated and before the MERGE; the two-statement form applies the MERGE on top of it (guard bypassed), the atomic form fails at commit with a conflict, applies nothing, and succeeds on the caller's retry.
- **Tier 3** keyed on `loans.loan_id`: `current_balance` after the run (the `MERGE` must subtract exactly once per loan; a cursor-faithful loop that double-applied would show here). A shadowed `p_servicer_id` (all servicers processed) shows first as a Tier 1 count delta on `payments WHERE batch_id = <batch>`.
- **Failure-injection replay** (Tier 4, on the migration catalog only): force the `MERGE` to fail (e.g. a NOT NULL violation via a seeded bad row) and assert Tier 1 on `payments` delta = 0, `audit_trail` delta = exactly 1 (the `BATCH_START` row with `record_count` 0 and `new_value` NULL, which is what the source's `error_handler` leaves too; a handler that deleted it, or one that left the `run_key` in `new_value`, both fail this Tier 3 on `audit_trail`) and Tier 3 on `loans` = pre-run values including `modified_date` (nothing in the block committed). A second replay commits a concurrent balance write to a waterfall loan while the block is open and then lets the block reach its commit: the block must fail with a conflict and the concurrent value must survive untouched (the earlier delta-reversal handler would have added `principal_due` on top of it, and a snapshot restore would have erased it). Without the atomic block the first replay leaves N payments and N+1 audit rows with unchanged balances. A third replay that fails the snapshot itself (e.g. revoke `SELECT` on `escrow_accounts` in the migration catalog) must still leave that one `BATCH_START` row and return its `audit_id` in the error message: the converted statement order is the source's (Step 1 batch record, Step 2 snapshot), so a conversion that creates the temp table first fails this replay with `audit_trail` delta = 0. Not verifiable on the fixture.
