Playbook: Front door for operational database estates (Sybase ASE, SQL Server OLTP, Oracle OLTP, DB2, on-prem PostgreSQL/MySQL) whose target is Lakebase Postgres, not a warehouse. Thin intake that pins the engine, splits the estate into the operational and analytical tracks, loads the dialect skill, sets OLTP-family defaults, and then runs `!dbx_migrate_pipeline` in the same session. No migration method lives here.

## Overview
The customer says "we're moving our loan-servicing database off Sybase." A warehouse front door would put the tables in Delta and the procedures in DBSQL, and the application that issues 400 single-row transactions a second would have nowhere to go. This playbook turns the request into a configured run of the standard chain with the **operational track** selected: transactional tables, constraints, procedures, and the applications that call them land in Lakebase Postgres (via `target-routing` → `databricks-lakebase`); the reporting and batch surfaces that read the same database land in Delta on the analytical track, fed from Lakebase by lakehouse sync. Everything after intake is the standard chain, unmodified, with the OLTP family defaults below.

## What's Needed From User
- The engine and version, and read access for Devin to the system catalogs (`sysobjects`/`syscomments`, `sys.*`, `ALL_*`, `information_schema`) plus, if it exists, an application-inventory or connection-string census: the applications are the D4 consumers of an OLTP estate, and they are found in config files and connection pools, not in query history.
- The **track split**: which schemas/tables the applications write (operational track, Lakebase) and which are read by reports, extracts, or batch jobs only (analytical track, Delta). If the user cannot say, propose the split from write-statement provenance in the procedure inventory and mark it PROPOSED.
- Whether the source engine can expose a change feed (SQL Server CT/CDC, Postgres logical decoding, Oracle redo, Sybase replication agent) and who owns enabling it. This decides between CDC coexistence and a freeze-and-load cutover, and it is a D10 the customer DBA performs; the migration principal never enables it.
- The transactional expectations that a warehouse migration never asks: isolation level relied on, identity/sequence contracts, trigger side effects, cross-table constraint chains, and the RPO/RTO the application tolerates at cutover. These become tolerance rows at STOP A.

## Procedure
1. **Consume the intake template first**: if a filled `00_intake_template.md` was attached or committed, load it, mark its rows FACT, probe the environment to fill what it left blank (DISCOVERED), and propose defaults for the rest (PROPOSED). Ask live only what neither the template nor a probe can answer.
2. Pin engine and version; probe catalog access with one live metadata query; register D10s for anything blocked, including the change-feed enablement and the Lakeflow Connect gateway network path.
3. Attach the matching dialect skill: list `skills/*/SKILL.md` in the installed plugin and pick by name (`tsql-ssis` for SQL Server / Sybase T-SQL, `oracle-plsql`, as they land). Never claim a skill exists because a recon adapter or Lakebridge dialect flag exists for the engine. If none exists: generic ANSI translation plus a build-the-skill wave-0 item from `skills/_dialect-skill-template.md`, stated plainly at intake. Load `target-routing` alongside it; the operational track's conversion target is Lakebase Postgres 17 (PL/pgSQL for procedures, Postgres constraints and sequences), the analytical track's is DBSQL/Delta as in the warehouse front door.
4. Set family defaults for the chain: unit = table group with its constraints, triggers, and the procedures that write it (a procedure and the tables it mutates are never split across units); lineage extraction = procedure write-sets + foreign-key graph + application connection census; the SQL profile and a **LAKEBASE** target profile are the dominant surfaces; coexistence = Lakeflow Connect CDC from the legacy engine into the migration catalog where a connector exists, with the application repoint as the single routing point at STOP E; a Lakebase **branch per batch** is the isolated namespace (copy-on-write, TTL set, dropped on wave close), so children never share a schema.
5. Record the track split in `.migration/00_context.md`: every in-scope schema/table tagged `operational` or `analytical`, with the tag's provenance. Analytical-track units run the warehouse family defaults from `11-front_door_warehouse.md`; the two tracks share one dependency register, one ledger, and one STOP sequence.
6. Record intake facts in `.migration/00_context.md` shape. Record `stop_mode` (default `soft`; `hard` only if the user asks). Then run `!dbx_migrate_pipeline` **in this same session**, right away. Do not open a new session, do not ask the user to run it, do not stop here. The user's next message from Devin is STOP A.

## Specifications
- Deliverable: configured hand-off: engine pinned, access probed, track split recorded with provenance, dialect skill attached, LAKEBASE profile requested from setup, family defaults recorded.
- Validation: `!dbx_migrate_pipeline` was invoked in this session and the orchestrator can start ingest without re-asking anything this intake covered; every in-scope table carries a track tag.
- Reconciliation for operational-track units runs the harness in `--mode transactional --target-kind lakebase` against the migration branch: both sides are pinned for a consistency window (source `SNAPSHOT` where the engine allows it, otherwise open/close markers and `isolation: none` on the record), rows newer than the target's applied CDC watermark are in flight rather than defects up to `cdc_lag_max_s`, and tiers 5-7 add PK-set diff, lag/ordering, and constraint/index/sequence parity. Every unit's mapping must name a `watermark` column and, for identity tables, `identity`; a table with no watermark is graded strictly and the tolerance record's `cdc_lag_max_s` is a STOP A row, not a child default. A unit whose source cannot be pinned and has no watermark is DEGRADED recon, not a lower tolerance.

## Advice and Pointers
- The OLTP estate's difficulty is procedural and transactional, not volumetric: a 40 GB Sybase database with 900 procedures is a harder migration than a 40 TB warehouse. Weight the complexity ranking by procedure count, trigger count, and cross-table constraint depth.
- Applications are the consumers. A D4 sweep that finds dashboards but not the three services holding connection pools has failed; ask for the deployment inventory and grep configuration repositories for connection strings.
- Lakebase branches are the family's cheapest correctness tool: a child converts into a branch, recon runs against the branch, wave close drops it. Never convert into the `production` branch of the target project.
- Identity/sequence semantics, `@@IDENTITY`-style session state, and trigger ordering are where like-for-like breaks silently; they need explicit rows in the dictionary and in the tolerance record.
- Where the application cannot be repointed to Postgres wire protocol without code changes, that is a D4 rebuild decision at STOP C with an application-team owner, not something the migration writes.

## Forbidden Actions
- Do NOT begin inventory, analysis, or conversion here; hand off to the chain.
- Do NOT enable CDC, change tracking, replication, or logical decoding on the legacy engine; register the D10 and name the owner.
- Do NOT put operational-track tables into Delta because it is the path the warehouse front door knows; the track split is a STOP A fact.
- Do NOT run `--mode transactional` against a Delta target or without a per-table watermark in the mapping; the CLI refuses the former and the harness grades the latter strictly.
