Playbook: Turn one pipeline's analysis into an executable plan: every dependency DECIDED, every lead-time request fired, the fan-out width and gates confirmed, and the whole thing approved by the user at STOP C.

## Overview
The plan is the contract between the human stops and the parallel execution machine. After STOP C approves it, waves run without further design decisions: children convert, recon gates grade, the orchestrator sequences. Anything still ambiguous after this playbook is a defect of the plan, not a judgment call for a wave child.

```
<Pipeline>_analysis.md  ->  dependency decisions (decide mode)  ->  scaffolding delta
                        ->  execution schedule (waves x batches x width)  ->  recon gate spec
                        ->  <Pipeline>_plan.md  ->  STOP C (blocking)
```

## What's Needed From User
- Presence at STOP C: this playbook ends in the single most consequential approval of the engagement.
- **A decision on every UNDECIDED dependency** (via `!dbx_dependency_resolution` decide mode).
- **Fan-out width confirmation**: proposed default 20 concurrent children (bounded by the D10 concurrency facts); the user may widen or narrow per wave.
- **Gate posture**: recon-green-required-to-merge per unit (default, strongly recommended) vs batch-level gating; STOP D posture (notify per wave vs pause per wave).
- Data-load posture for the coexistence window: federation-only reads (default) vs materialized backfill of input tables, per the DATA/DEPENDENCY profile.
- **The review contract**: who reviews and merges the wave PRs, their turnaround SLA, and the review tiering. Propose as the default: recon-green plus independent-recon-pass earns a lighter review tier (spot-check plus evidence-format check), with full review reserved for recon-flagged units and the first unit of each pattern class. Reviewer throughput is a real term in the wall-clock math, not an externality; review effort follows risk, not uniformity.

## Procedure
1. Verify inputs: analysis current, target profiles present for every workload type in the unit inventory, tolerances confirmed. Route back on any gap.
2. **Decide every dependency**: run `!dbx_dependency_resolution` in decide mode over the pipeline's UNDECIDED entries. Fire every lead-time request and record it. No entry may remain UNDECIDED past STOP C.
3. **Specify the scaffolding delta** (wave 0 work beyond shared objects): target catalog/schemas, backfilled or federated input tables, CI skeleton, the recon harness wired to this pipeline's queries and tolerances, and Asset Bundle/Workflow shells per the profiles. Reuse what exists; never fork it.
   Where the data-load posture is materialized backfill, **specify the backfill by size tier**: small tables via CTAS through federation; large tables via partitioned incremental copies with checkpointing and per-partition verification (counts plus aggregates per partition); very large or CDC-fed tables need an ordering rule against in-flight changes (backfill to a watermark, then CDC catch-up) and their own line in the wall-clock math. A backfill too big for CTAS is a wave-0 workstream, not a footnote.
4. **Write the execution schedule**: the analysis's waves and batches, each batch with its unit list, branch name, target-profile references, recon plan rows, the idempotency rule (drop-and-recreate of the batch's isolated area on every run), a **disjoint namespace slice per child** (the harness parameterises by namespace, so two batches touching the same logical table names still never collide; a write-target collision that a namespace slice would have dissolved is a plan defect, not a reason to serialize waves), and every input artifact the child needs (children share no filesystem or memory with the parent). State the width per wave, the **legacy-query concurrency cap** (from the tolerance record; may bind tighter than session width), the **circuit-breaker threshold** (default: 3 children reporting the same failure class pauses remaining launches), and the projected wall-clock: `serial floor + (widest wave / width) + reviewer throughput per wave`, not a hand-wave. Assign each unit a **parallel-run window tier** (e.g. reference lookups: short / standard: medium / money-path and ML scoring: full window plus period-end boundary) so easy units stop paying the worst-case coexistence calendar; cutover eligibility arrives per tier.
   Write each wave as a manifest at `.migration/waves/wave-<N>.json` (shape documented at the top of `skills/migration-fanout/workflow.py`): repo, child and verify macros, width, breaker threshold, auto_merge, and one entry per batch with its id, units, declared write targets, and the complete brief text. This file is what launches the children, so a batch with a missing brief or an undeclared write target is a plan defect that the workflow will refuse. Commit it before STOP C.
   Size each unit (S/M/L/XL); XL units get the **decision-first 2-PR split** (a ~100-line contract/decision PR signed before implementation, then the implementation PR); everything else ships as one collapsed PR per unit, never a diff-split stack.
   **Batch sizing is a cost lever**: small/simple units batch at 4-5 per child to amortize per-session startup cost; complex or high-risk units run 1-2 per child so a failure does not strand green work in the same session. The pilot wave measures actual per-unit session cost, and the plan re-batches waves 2..N on the measurement, not the guess. Where a session platform offers lighter session tiers, price mechanical passes (launch-only, verify-only) separately from conversion/triage children in the compute-cost line of the plan. For pipeline 2..N of an engagement, state the expected per-unit discount explicitly (profiles, dictionary, and hardened skills carry over; typical 30-50%) and re-baseline from pipeline 1's measured cost, so a regression is visible rather than vibes.
5. **Specify the recon gate mechanically**: for each batch, the exact commands or queries the child runs, what PASS means (per the tolerance record), and the evidence format the PR must carry. The gate must be executable by a session that has read nothing but the plan and the `.migration/` workspace. The gate spec must also pin the **evidence-integrity terms** that field runs show cause most review bounces: per check, the exact population it is computed over (a rate diluted by a superset population is the classic silent miss); the baseline source per check (never data the unit itself generates); what counts as idempotency evidence (a run that wrote rows); the fixture seed volumes and environment-ownership statement each child's hand-off carries; the **declared source-volume assertion** per table (the row volume the source actually holds, so green on self-generated data is structurally impossible); the **run-mode budget** (children iterate `fixture`, live proof is the parent's single window per wave, with any child live budget stated explicitly); the **review-round cap** (default 3 after self-check, then escalate); and the **full-re-run cap** per unit (default 3) beyond which the child escalates instead of re-running.
6. **Pilot and calibration rule**: wave 1 runs deliberately narrow (width <= 5) regardless of confirmed width, to tune the dialect skill and surface systematic conversion errors before they multiply across 50 children. Corrections land in the skill and knowledge notes before wave 2 fans out fully. The same logic applies **per pattern class, not just per engagement**: when a later wave introduces a new unit class (the first aggregation-layer unit, the first report unit, the first CDC unit), the schedule runs one deliberately small calibration unit of that class first, harvests its dictionary/skill feedback, and only then briefs the rest of the class, in parallel. Serializing whole waves because each unit might teach something is the expensive version of this rule; calibrate on one cheap unit, then fan out.
7. **Governance mapping section**: with the `governance-mapping` skill, turn the governance inventory rows touching this pipeline into the proposed UC mapping (grants -> UC GRANTs and groups, masking/row policies -> UC masks and row filters), with every unmappable row flagged GAP. Policy-design questions (group restructuring, PII regime changes) become D-entries with a human owner, explicitly outside automation scope. The mapping and its gaps are attached at STOP C for the security reviewer's approval; the executable script is generated from approved rows only.
8. **Write `<Pipeline>_plan.md`** with all of the above plus the risk register (INFERRED types, unresolved-contract blockers now cleared or accepted, lead-time exposures). Update the ledger.
9. **STOP C (blocking)**: attach the analysis and the plan; present the dependency decision table with fired requests, the schedule with width and wall-clock projection, the gate spec, the governance mapping with its GAP rows, and the scaffolding delta. Get explicit approval before any execution session launches.

## Specifications
- Deliverable: `<Pipeline>_plan.md`, every dependency DECIDED with fired requests, approved at STOP C.
- Validation: (1) no UNDECIDED entries; (2) every batch is self-contained (a child needs nothing outside its hand-off); (3) the gate spec is mechanical; (4) the pilot wave is narrow; (5) the user approved explicitly, on this run, even if a prior session produced an earlier plan.

## Advice and Pointers
- **The wall-clock math is the sales story and the honesty check.** State it explicitly: a 400-unit pipeline at width 20 with recon gating is ~3-4 sessions of wall time after the pilot, plus lead times. Lead times usually dominate; say so.
- Batch hand-off completeness is the most common fan-out failure. The test: could a session with amnesia execute the batch from the plan alone? If not, the plan is not done.
- Recon-green-to-merge per unit is what keeps review burden flat as width grows. Resist batch-level gating unless recon cost genuinely forces it.
- The pilot wave is not optional caution, it is the mechanism that makes waves 2..N cheap: systematic dialect errors found once instead of fifty times. Same for the circuit breaker: it is the single highest-leverage compute-cost control in the plan; a trap caught at 3 children costs 3x, uncaught it costs the full width in conversion plus remediation.
- Above ~10 batches per wave, the dynamic-workflow rule is a cost rule as much as a reliability rule: a deterministic script does the launch/wait/gate loop, and the orchestrator agent spends its time only on exceptions and wave close.

## Forbidden Actions
- Do NOT let anything past STOP C with an UNDECIDED dependency or an unfired lead-time request.
- Do NOT write conversion code or launch children here.
- Do NOT hand a child a batch that references artifacts not committed or not listed in its hand-off.
- Do NOT skip or widen the pilot wave, and do NOT project wall-clock without stating the serial floor, lead-time exposure, and reviewer throughput.
- Do NOT auto-approve on a resumed run; STOP C fires every time.
